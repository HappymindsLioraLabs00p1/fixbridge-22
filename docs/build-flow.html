System design · where it runs

Three services, each doing the one thing it is good at

The browser only ever talks to one origin — the Netlify site. Everything under /api/* is rewritten server-side to the backend, so there is no CORS negotiation in the browser and no mixed-content problem. That single hop is the reason sign-in works at all, and it is where two days of debugging went.

The core mechanism

Two prices, one of which nobody outside the platform may see

This is the product. A contractor bids a net price they want to be paid. A server-side pricing engine — never the AI — converts that into the retail price the customer is quoted. The difference is the platform's margin, and the whole system is built so that number cannot leak.

The job lifecycle

reported→ awaiting_service_payment→ awaiting_contractor→ bid_received→ proposal_sent→ scheduled→ work_completed→ customer_review_pending→ admin_review_pending→ paid_out

The coral state is a hard gate: no money reaches a contractor until the customer confirms the work, and confirmation is refused while a change order is still outstanding.

The question you asked

Is this a website, or an app?

It is one responsive web application that behaves as both — and it is not a native mobile app. The same URL serves the public marketing site and the signed-in product; which one you get depends on whether you are logged in and what role you hold.

SurfaceRouteStatus

Customer app/customer · /customer/report · /customer/jobs/[id]built

iOS / Android native appno React Native or Swift projectnot built
If a real mobile app is wanted, the backend is already the right shape for it — it is a plain JSON API with JWT auth, so a React Native or native client would consume the same endpoints with no server changes. The realistic middle step is making the existing site installable as a PWA: an icon on the home screen, no app-store review.

Not finished

What is still open

  • The site is private. Netlify SSO is still on, so only the account owner can open the link. This is one toggle, and nothing else matters until it is flipped.
  • The database move is mid-flight. Render's blueprint was overwriting the connection settings; that is fixed in code, but the switch to Neon needs a blueprint sync and the variables set once in the dashboard.
  • Live integrations are unproven. Stripe, Twilio and Resend have never run against real keys — every one of those paths is exercised only by stubs.
  • Deferred by design: admin MFA, DIY plans, landlord and agent dashboards, partner referrals, direct-lead mode, property profiles.
